以下仅依据所给代码静态审查，未执行任何操作。按影响列出 **8 个实质问题**：

1. **项目黑名单不能跨来源生效**
   - **位置**：`collectors.py::git_repositories/git_events/lark_events/browser_events`
   - `project_ids` 只检查事件的 `project_id`，但实际上只有 Codex 元数据提供这个字段。Git 从 Codex 发现仓库时，反而丢掉了线程的 `project_id`，仅用 `source="git"`、`cwd` 和目录名判断。
   - **触发与影响**：只将某项目 ID 加入黑名单，该项目的 Codex 会话被挡住，但其目录仍会作为 Git 扫描根，提交和状态照常读取。飞书、浏览器也没有项目归属关联。因而当前“项目黑名单”只是部分来源的字段过滤，不是项目整体拦截。

2. **路径黑名单只检查资源入口，不能阻止读取资源内部的被禁路径**
   - **位置**：`collectors.py::git_events/codex_events`
   - Git 对仓库根目录检查后，直接读取完整提交的文件列表及整个仓库的 `status`，没有针对变更文件应用路径黑名单。Codex 检查的是 `cwd`，真正打开的 `rollout_path` 没有检查。
   - **触发与影响**：允许 `/repo`、禁止 `/repo/private` 时，`private` 下的文件仍可能进入提交证据和状态快照；禁止某个 rollout 文件路径也不会阻止打开它。发现阶段剪枝不能替代实际读取对象的检查。

3. **当天尚未结束就被永久标记完成，晚间新增数据不会自动补读**
   - **位置**：`cli.py::due_days/main`
   - 到达配置时间后，`due_days()` 将**今天**作为截止日；运行成功立即保存 `last_completed_day=今天`，后续调度只考虑下一天。
   - **触发与影响**：例如每天 18:00 运行，18:00—24:00 的消息、提交和浏览记录不会再自动读取；当天较晚发生的会议也只能拿到提前读取的元数据。若需求是完整自然日复盘，应在次日收齐，或明确支持当天反复更新与封账。

4. **采集失败仍可能报成功，并推进完成日期，导致缺失永久不重试**
   - **位置**：`cli.py::collect/run_day/main`，`report.py::build_report`
   - `collect()` 捕获各来源异常后只记录 `error/partial`；`run_day()` 最终的 `ok` 由模型报告是否成功决定，与采集是否完整无关。
   - **触发与影响**：飞书认证失败、浏览器无权限，甚至所有来源都失败时，只要模型成功输出报告，调度仍推进 `last_completed_day`，不会触发失败退避或自动补采。`--no-ai` 更是无条件返回 `ok=True`。此外，`tick` 的失败埋在 `runs` 数组中，顶层没有 `ok=False`，进程仍返回退出码 0。

5. **重跑只有新增和覆盖，没有清理失效事件，报告会混入旧数据**
   - **位置**：`core.py::Store.put/events`，`cli.py::collect`，`report.py::build_report`
   - 每次采集仅按 ID upsert；本轮没有返回的旧事件从不删除，报告读取的是当天全部历史缓存。
   - **触发与影响**：Git 未提交状态恢复干净后，旧状态快照仍保留；已删除的提交、消息或任务也可能继续出现在报告中。将某来源配置为 `enabled=false` 后，其旧事件仍会参与报告，因为 `Store.events()` 不检查来源开关。最终会出现覆盖说明为“禁用/0 条”，正文却引用旧记录的矛盾。

6. **长时间睡眠或停机后，补跑窗口之外的日期会被静默永久跳过**
   - **位置**：`cli.py::due_days/main`
   - 补跑起点被限制为 `end - (catchup_days - 1)`，没有把被截掉的未完成日期记录为缺口；窗口内运行成功后，又把全局完成游标推进到最新日期。
   - **触发与影响**：默认 `catchup_days=3`，停机十天后只补最后三天，更早的未完成日期此后再不会被自动考虑。这里不是暂时限流，而是永久丢弃待处理日期，不能保证睡眠后的完整补跑。

7. **默认 Git 发现硬依赖 Codex 数据库，Codex 不可用会连带阻断全部 Git 读取**
   - **位置**：`collectors.py::git_repositories`
   - 默认 `discover_from_codex=True`，而 `codex_threads()` 在扫描任何 Git 根目录之前调用，异常没有在发现阶段隔离。
   - **触发与影响**：没有安装 Codex、数据库不存在或不可读时，即使明确配置了有效 Git `roots`，整个 Git 采集也会直接失败，已配置仓库一个都不会扫描。这违反了各来源应可独立运行的预期。

8. **飞书日历响应解析会把未知结构误报为空成功，也没有处理分页和全天日期**
   - **位置**：`collectors.py::lark_events` 日历分支，`core.py::stamp`
   - 日历直接调用一次 `cli()`，不走 `pages()`；非列表响应只取 `events/items`，字段不匹配就默认 `[]`，不报解析错误，也不检查 `has_more`。
   - 同时，`stamp()` 虽支持 `{"date": ...}`，但纯日期如 `2026-06-01` 会解析成无时区时间后被主动拒绝，因此这种全天日程会使日历分支失败，后续条目也不再处理。
   - **影响**：响应结构变化可能显示“成功、0 条”，分页会漏后续日程，全天日期记录则可能中断整个日历分支。
