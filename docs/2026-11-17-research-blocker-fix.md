## 查证与修复

1. 在隔离数据库和保存的实际输入上复现会议姓名研究。模型接口返回文本为两个连续且相同的 lookup_evidence JSON 对象，解析器在第 93 个字符拒绝。原生产日志没有保存响应体，因此不能断言当时两个 JSON 的内部来源；复现结果确认同样输入链路确会产生该协议错误。现增加一次单 JSON 协议纠正，仍失败则退避，不截取第一个对象冒充完整结果；异常输入和返回保存在 runtime/research-failures/。
2. 接听动画研究保留 57 条直接证据，原逻辑按原始字符数加入相关事件：89 条、118739 字符，但下游无损编码为 120929 UTF-8 字节，超过 120000 上限；随后事实提取仍可能超预算。现按相同无损编码的字节数选择相关事件，实际全关联输入复验为 88 条、119508 字节，57 条直接证据全部保留且不调用摘要模型。其余关联事件仍可回查；直接证据本身过大时仍走现有完整分片及保真审查，不删除种子。
3. 研究失败按机会 ID 单独累计，发现阶段另行计数。某条目成功不清除其他条目的失败；持久故障通知包含研究标题和错误原因，并保留同一故障去重和六小时提交冷却。

部署前保留源码与 SQLite 快照；停止旧研究进程后，仅删除混合不同任务的旧全局告警计数。条目尝试次数、退避、队列、检查点和通知冷却保留，再启动原 launchd 服务加载修改。实际 blocking-check 返回 blocked=false，研究服务处于运行状态。
